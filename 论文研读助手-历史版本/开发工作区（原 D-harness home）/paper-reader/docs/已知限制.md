# 已知限制

按影响程度排列。每条都注明当前行为与用户可采取的应对方式。

---

## 一、扫描件与无文本层 PDF（重要）

- **现象**：整页是扫描图片的 PDF 抽不出任何文字，参考分析的 13 个字段全部返回
  `not_found`（"原文未说明"），界面仍可正常阅读、批注、填写阅读卡。
- **原因**：本工具**不做 OCR**。内置解析器与 `pdftotext` 都只读取 PDF 里的文本层。
- **已验证**：`finance-2021-zhang.pdf` 是一篇 15 页的扫描件，抽取结果为 0 文本，
  分析完成后字段全部为 `not_found`，且该论文的人工保存与导出照常可用。
- **应对**：先用 OCR 工具（如 Adobe Acrobat、ABBYY、`ocrmypdf`）生成带文本层的 PDF，
  再导入本工具；或直接手写阅读卡。

## 二、伪文本层（罕见但会误导）

- 某些中文期刊排版会嵌一层几乎不可见的文字（96% 空白、质量评分却很高）。
  阶段 2 已加入 `is_junk_text` 判定把这类论文标记为不可用文本；
  但判定是启发式的，极少数论文仍可能抽出一堆看似正常、实际错位的文字。
- **应对**：如果参考分析的引文读起来不像人话，请以 PDF 原文为准，不要采信该次分析。

## 三、本地模型要求

- **必须自备**推理服务（Ollama / LM Studio / 其他 OpenAI 兼容接口）。软件不内置模型、不下载模型。
- 建议模型规模：**7B 以上、支持中文的指令模型**（如 `qwen2.5:7b`）。更小的模型经常无法
  稳定输出满足 Schema 的 JSON，表现为 `failed / validation_failed`。
- 上下文长度：单次请求的原文预算为**中文约 28 000 字 / 英文约 36 000 字**（超出即截断）。
  参考文件的 `input` 区块会记下实际送入的页码与是否截断，界面顶部也会写明
  "本次只送入第 X–Y 页"。因此**跨章节的整体判断可能不完整**，结论与稳健性栏目尤其容易
  落在预算之外。
- 想要覆盖全文：可以先用"导出 Markdown"分段阅读并手写结论，或把论文拆成两半分别导入。
- 显存/内存：7B Q4 约需 6 GB 显存（或 8–10 GB 内存做 CPU 推理）。

## 四、长论文耗时

| 场景 | 量级 |
|---|---|
| 20–40 页，7B Q4，GPU | 30–90 秒 |
| 20–40 页，7B Q4，纯 CPU | 3–10 分钟 |
| 60 页以上（如 57 页的英文论文） | 约为上面的 1.5–2 倍 |
| 需要一次修复（首次校验失败） | 再增加约 1 倍时间 |

- 单请求超时 900 秒，超过即 `failed`（`error_code=timeout`），可重试。
- 并发固定为 1，多篇论文会排队；界面上能看到"已排队/正在生成/进度"。
- 强制重跑会重复消耗算力；使用外部接口时还可能产生调用费用。

## 五、分析质量与校验边界

- 校验保证的是**格式与引文可核对**，不保证结论正确：引文真实不代表概括准确。
- 因果判定是**启发式**（动词/词组表 + 引文中的识别词）。明显的"导致/降低"越界会被拦下，
  更隐晦的因果暗示可能漏判。
- "原文未说明"的判定依赖模型自觉：校验只能保证格式（`not_found` 时 answer 必须是
  "原文未说明"），无法判断模型**本应**说 not_found 却编了内容——这需要你回到原文核对。
- 页码写错但引文真实时，软件按实际页码修正并记入 `verification.corrections`（不判失败）；
  页码越界才是硬错误。

## 六、界面与交互

- 滚轮翻页**只作用于 PDF 区域**：鼠标停在笔记栏或工具栏上滚动不会翻页（有意避免误伤笔记滚动）。
- 原文区默认给足高度（1366×768 下可用高度约 525 px），但整页缩放在小屏上仍会把正文缩到
  看不清，因此软件自动改用"适合宽度"（实测 11 px）并提示一次；一页需要滚动才能看完，
  滚到边界后滚轮才翻页。窗口放大到 1920×1080 及以上会自动切回"适合页面"（整页可见）。
  判断阈值是缩放系数 0.78（屏幕上正文高度约为该系数的 9.5 倍）；你手动选过缩放下拉之后，
  软件不再自动切换。
- 想在小屏上一次看更多字：点工具条右上角的**收起记录栏**，原文区会占满整个宽度
  （实测正文 16.8 px），需要记录时再展开。
- AI 展开状态刻意不持久化：刷新页面或切换论文后收起（避免把 AI 内容当成人工记录）。
- 触控板惯性滚动期间只翻一页（600 ms 防抖锁）。
- `max_concurrent_jobs` 改动需重启服务生效。
- `terms` / `reader_questions` / `warnings` 已生成并保存在答案文件里，但界面上还未展示。

## 七、检索与规模

- 文献列表是本地过滤（标题/作者/主题），没有全文检索，也没有向量检索。
- 库规模在数百篇时性能没有问题；上千篇时初次加载会变慢（前端一次性读取 `/api/state`）。
- 所有数据都在这台机器上：`data/` 目录是唯一数据源，请自行纳入备份计划。

## 八、导出与同步

- Markdown 导出**不含** AI 参考内容（设计如此，避免把未核对的文本带进笔记）。
- Obsidian 同步只写自动区域（`<!-- paper-reader:start -->` … `end`），"我的补充"区域永不覆盖；
  若标记被破坏，同步会报错并保留原文件不动。
- 同步是单向的：软件 → 笔记库；在 Obsidian 里的修改不会回写到软件。

## 九、隐私

- 使用本机 Ollama / LM Studio（默认回环地址）时论文原文不出本机。
- 一旦把 `base_url` 改成局域网或公网地址（含 `openai_compatible` 指向第三方），
  论文原文会发送到该地址；软件不做拦截或脱敏，请自行确认对方政策。
- 日志只记录 provider / model / 耗时 / 错误类别，不含论文正文，也不含密钥。
  上游服务返回的错误正文只保留**首行、最多 120 字**并做脱敏后才写进库里，避免把网关回显的
  请求内容或凭据带进文献库。
- `run/startup.log` 只保存事件行；超过 2 MB 会自动轮转为 `startup.old.log`。

## 十、环境

- 已验证环境：Windows + Python 3.13、Chrome 154。未在 macOS / Linux 上测试。
- 无第三方 Python 依赖（仅标准库）；PDF 渲染用随包分发的 PDF.js。
- 中文文本抽取依赖系统里的 `pdftotext`（TeXLive 自带）作为首选后端；缺失时自动退回内置解析器。
